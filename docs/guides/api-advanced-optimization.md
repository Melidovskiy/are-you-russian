## Начните с измерения

Соберите статистику по модели, числу запросов, входным и выходным токенам и времени ответа. Сравнивайте одинаковые задачи. Длинный контекст и повторная отправка истории могут увеличивать расходы даже при небольшом количестве видимых сообщений.

Записывайте поля usage и сведения о кешировании из ответа API. В текущей документации отдельно учитываются обычные входные токены, создание кеша и чтение кеша. Для разбора конкретного запроса сохраняйте исходную структуру usage, поскольку поля зависят от используемого endpoint и функций.

## Организуйте повторяемый контекст

Общую инструкцию, инструменты и стабильные документы удобно держать в повторяемой начальной части запроса. Изменяющийся вопрос пользователя размещайте после неё. Изменение общей части способно повлиять на попадание в кеш.

Сравните статистику двух последовательных запросов с одинаковым началом. Проверяйте реальные поля чтения и создания кеша. Поддержка со стороны клиента, шлюза и выбранной модели должна быть согласована.

Учитывайте срок жизни кеша, объём повторяемого контекста и актуальные тарифы. Для редко повторяющейся задачи подготовка большого кешируемого блока может оказаться лишней работой. Стоимость оценивайте по собственным измерениям и действующим условиям поставщика.

## Ограничьте контекст задачи

Передавайте файлы и историю, необходимые для текущего шага. Для длинной работы сохраняйте промежуточный результат и краткое описание принятых решений. При обрезке истории сохраняйте важные требования и сообщения об ошибках.

Оцените качество ответа после изменения контекста. Экономия токенов полезна, если задача продолжает выполняться с нужной точностью. Для повторяемых операций заведите небольшой набор примеров и сравнивайте результат на нём.

## Контролируйте скорость и бюджет

Ограничения запросов, токенов и расходов отражают разные условия. В документации описаны RPM, ITPM и OTPM. Значения для вашей организации смотрите в Console.

При 429 прочитайте тело ошибки и наличие `retry-after`. Ограничение бюджета может требовать действия в кабинете, поэтому бесконечные повторы только увеличивают число неудачных запросов. Установите собственный предел расходов и уведомления там, где они доступны.

Сохраняйте сводную статистику отдельно от чувствительных prompt. Для расчёта затрат обычно достаточно числовых полей, названия модели и времени запроса.
